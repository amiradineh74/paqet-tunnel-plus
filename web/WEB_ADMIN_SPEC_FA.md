# Paqet Tunnel Plus — Web Admin specification (فارسی)

> نسخهٔ طراحی 2026-10-23 — مبنای توسعه. **هنوز پنل کامل ساخته نشده است.** این سند شرایط پذیرش نسخه عمومی را مشخص می‌کند. راهکار فعلی `web/` فقط‌خواندنی و local-only است؛ از بازکردن مستقیم پورت 8792 آن در اینترنت خودداری کنید.

## هدف
یک پنل وب فارسی (RTL)، واکنش‌گرا و امن مانند Manage Usage Port، قابل بازشدن از اینترنت با HTTPS و ورود مدیر؛ **تمام عملیات موجود در اسکریپت** باید رابط گرافیکی معادل داشته باشند. پشتیبانی مستقل از چند تونل، نقش ایران/خارج و چند سرور؛ اطلاعات و رفتار فعلی سرورها بدون عملیات صریح کاربر تغییر نکند.

## معماری
1. **پنل مرکزی:** HTTPS و ورود امن، فهرست و وضعیت همزمان ایران/آلمان/ترکیه، مدیریت نشست، کنترل دسترسی، تاریخچه و گزارش.
2. **Agent سبک روی هر سرور:** اجرای فرمان‌های allowlisted بدون shell و با scope محدود به یک سرویس، گزارش سلامت واقعی؛ ارتباط به پنل از مسیر امن، بدون SSH سرور به سرور. از اتصال outbound/poll برای سرورهای پشت محدودیت شبکه پشتیبانی شود.
3. **موتور عملیات:** هر ویرایش YAML/iptables/هسته یک transaction شامل snapshot، dry-run/validation، نمایش diff بدون secrets، تأیید صریح، health check و rollback دارد.
4. **موتور آزمون دوطرفه:** تونل تست مستقل با سقف مدت و ترافیک، آزمون مسیر واقعی و نمایش progress در هر دو طرف؛ نیازمند هماهنگی زمان UTC و تایید تطابق هسته و کلید (هش).
5. **ذخیره‌سازی:** SQLite محلی پنل برای inventory، audit، test runs، metrics و backup metadata؛ کلیدهای حساس در agent و خارج از گزارش/لاگ وب.

## الزام‌های امنیتی برای پنل اینترنتی
- هرگز Python HTTP فعلی یا API با دسترسی روت را مستقیم روی `0.0.0.0` منتشر نکنید؛ reverse proxy با HTTPS روی دامنه معتبر الزامی برای تولید.
- احراز هویت با رمز هش‌شده مقاوم، session محدود، cookieهای `Secure/HttpOnly/SameSite`، MFA اختیاری، نرخ‌محدودسازی/قفل موقت و CSRF برای POST/PUT/DELETE.
- عامل‌ها باید با هویت/کلید مستقل ثبت شوند؛ ارتباط رمزنگاری‌شده و محدود به دستورات تعریف‌شده؛ هیچ shell / eval / raw command از مرورگر پذیرفته نشود.
- جلوگیری از تغییر همه سرویس‌ها با یک کلیک؛ نام سرویس و مسیر YAML whitelist شوند؛ per-operation locks؛ restart-safe backup و rollback برای تغییرات جفت‌سروری.
- secrets هرگز به UI، localStorage، Audit یا API عمومی نروند. لاگ‌ها redaction و محدودیت خروجی داشته باشند.
- به PasarGuard و پایگاه داده آن هیچ نوشتنی انجام نشود؛ این پنل مستقل است.
- برای راه‌اندازی اینترنتی، DNS، پورت 443 و گواهی TLS معتبر ضروری‌اند؛ اگر کاربر دامنه ندارد، دسترسی با IP نیاز به راهکار گواهی معتبر یا حالت آزمایشی مشخص دارد.

## معیارهای پذیرش
1. کاربر از مرورگر خارج شبکه به `https://panel.example.com` دسترسی داشته باشد؛ بدون login هیچ API مدیریتی جواب ندهد.
2. از یک صفحه وضعیت ایران و خارج مشخص باشد؛ سرور قطع، `unknown/offline` نشان داده شود نه `healthy`.
3. هر قابلیت CLI معادل عملیاتی وب و تست یکپارچه داشته باشد؛ Preview به‌عنوان عملیاتی معرفی نشود.
4. اجرای هر تغییر با ذخیره نسخه پیشین، validate و health check روی همان سرویس همراه باشد؛ rollback در تست شکست قطعی انجام شود.
5. تست سرعت، پهنای‌باند اینترنت سرور را با توان تانل اشتباه نگیرد؛ traffic cap قابل تنظیم داشته باشد.
6. installer به‌صورت opt-in باشد؛ صرف آپدیت اسکریپت هیچ سرویس یا فایروالی را عوض نکند.
7. تست end-to-end در محیط staging و تست قطع شدن ناگهانی در میانهٔ عملیات قبل از انتشار production انجام شود.
